## Open decisions (ask the user, do not guess)

- [x] **DECIDED:** Maven, with the Maven wrapper (`backend/mvnw`).
- [x] **DECIDED:** Java 25 (LTS), Spring Boot 4.1.1 (pinned via `spring-boot-starter-parent`).
- [x] **DECIDED:** Auth uses a server-side Spring Security session (HttpOnly cookie, cookie-based CSRF token for the SPA), not JWT. Reason: instant revocation on logout/password change, simplest for a same-origin SPA behind nginx, STOMP reuses the cookie.
- [x] **DECIDED:** Password hashing uses Argon2id (`DelegatingPasswordEncoder`, `{argon2}` default, `{bcrypt}` match-only). Reason: Spring Security 7 BCrypt rejects passwords over 72 bytes, the password policy allows 15-128 characters.
- [x] **DECIDED:** Classic Spring MVC + WebSocket/STOMP (no WebFlux).
- [x] **DECIDED:** Project name is "Shipir". Base package is `dev.bethge.shipir`. Repo layout: `backend/` (Java/Maven) and `frontend/` (React/TypeScript).
- [x] **DECIDED:** Database and user are named `shipir`. The connection is configured via `DB_HOST`/`DB_PORT`/`DB_NAME`/`DB_USER` (defaults `localhost`/`5432`/`shipir`/`shipir`) and `DB_PASSWORD` (no default), shared by `application.yml` and `docker-compose.dev.yml`. Reason: a native Postgres on 5432 must be able to coexist with the Docker dev DB (`DB_PORT=5433`).
- [x] **DECIDED (shipr-r3w):** 'Stack' is renamed to 'deployment' everywhere (UI, API, code, DB via V16); a single deploy execution is a 'run' (`runId`). The `shipir.stacks.base-dir` / `SHIPIR_STACKS_BASE_DIR` setting, on-disk layout and compose project names are kept. Historic `STACK_*` audit rows are not rewritten.
- [x] **DECIDED (shipr-e42):** Stack directories live under `shipir.stacks.base-dir` (env `SHIPIR_STACKS_BASE_DIR`, `/data/stacks` on the `shipir-stacks` volume in hosting), one dir per `<host-id>/<stack-name>`; the DB (`stack_versions`) is the source of truth and files are rewritten on deploy.
- [x] **DECIDED (shipr-9sm):** AI chat assistant is in scope (was out of scope). Decisions are recorded in CLAUDE.md under "AI assistant".
- [x] **DECIDED (shipr-6ta):** The config editor works inside managed deployment directories (`<stacks-base>/<hostId>/<name>/`), no separate setting. `compose.yaml`/`.env` are excluded and the Git checkout `repo/` is read-only. Backups live in `<deployment dir>/.shipir-backups/<sha256 of path>/` (newest 10 per file, `shipir.config-editor.backups-per-file`), files are UTF-8 text up to 1 MiB, no separate `config_files` table (the directory is the source of truth), so the planned `create_config_files` migration is dropped.
- [x] **DECIDED (shipr-006w):** The AI assistant gets read-only tools for config files (list and read, same excludes as the config editor, `compose.yaml`/`.env` excluded entirely, env-like file contents never exposed, their names may appear in the tree as in the UI) and an ADMIN-only read tool for access grants. Write tools (config file edits, backup restore, permission grant/change/revoke) stay out of scope. Reason: both features are now built, and a model that changes files or access rights is a prompt-injection risk even behind Confirm. Recorded in CLAUDE.md under "AI assistant".
- [x] **DECIDED (shipr-bbzh.4):** OPERATORs may open container consoles, following the existing permission grants: OPERATE on the host or on the managed deployment that owns the container (VIEW only, no grant, VIEWER: refused; containers of other deployments/hosts are 404). It is OFF by default (`shipir.streaming.exec.operator-enabled=false`); ADMIN is unchanged. Open consoles end (ACCESS_REVOKED) when the grant or role goes away; EXEC_START/EXEC_END audit rows name the role. Consoles stay session-only: API-token requests always get 403. The UI reads the flag from `GET /api/exec/capabilities`.
- [x] **DECIDED (shipr-p4vd):** Container file access stays on the Docker archive API ("no exec"), with one narrow exception: when listing a directory hits the scan limit (`shipir.container-files.max-scan-bytes`), `ContainerFileServiceImpl.list` falls back once to a single-directory `find` via docker exec (argument list, no shell, normalised absolute path, NUL-separated output capped at 10,000 entries / 4MB). If exec is not possible (no `find`, distroless, stopped container) the result stays DIRECTORY_TOO_LARGE. Download and upload never use exec. Fallback entries carry name/type only (size 0, no mtime/mode).

- [x] **DECIDED (shipr-kqbc.36):** Non-ADMIN compose may only use named volumes of its own deployment: every top-level volume (explicit `name:` or external) must not exist yet or carry this deployment's `com.docker.compose.project` label; external volumes must exist and be own. Fails closed when Docker can't be asked. Shared volumes need an ADMIN deploy.
- [x] **DECIDED (shipr-kqbc.48):** Logs, stats, events and run output of system-managed deployments (the managed proxy) are ADMIN-only, consistent with the exec and REST locks; a demoted ADMIN loses them without reconnecting.
- [x] **DECIDED (shipr-kqbc.53, 2026-11-09):** A compose whose env_file/include/extends references use `$`, `~`, remote sources or paths outside the deployment directory gets no graph hash. Accepted and documented: such deployments stay restricted for automatic (system) runs until an ADMIN deploys by hand; there is no fallback to the "only Shipir's own files" rule (shipr-kqbc.55, .56).
- [x] **DECIDED (shipr-kqbc.61, 2026-11-13):** On remote (TCP) hosts `ComposeSecurityPolicy` rejects every bind mount (short and long syntax, relative `./x` too, also bind-type volumes via `driver_opts`) for non-ADMIN runs, and automatic/system runs follow the same rules as non-ADMIN (unless the version is ADMIN-approved as before). Error: 403 `REMOTE_BIND_MOUNT_DENIED`. Named volumes keep their ownership rules; LOCAL hosts and ADMIN deploys are unchanged.
- [x] **DECIDED (shipr-kqbc.52):** The volume-ownership check before `docker compose` is a documented time-of-check/time-of-use residual risk (Javadoc on `ComposeSecurityPolicy`).
- [x] **DECIDED (shipr-0qbh.54, 2026-11-09):** A deployment-level OPERATE grant covers start/stop/restart/pause/unpause/kill of that deployment's containers only. Remove, recreate, duplicate and resource edits stay at host OPERATE, because they change the deployment outside Compose (`HostResourcesService.requireOperate`, pinned by `HostResourceActionsAccessTest`).
- [x] **DECIDED (shipr-0qbh.67, 2026-11-13):** Removing a container of a Compose project (any compose label, incl. the system-managed proxy) is refused for every role with 409 `MANAGED_BY_COMPOSE`, like recreate/duplicate/resources (`HostResourcesService.removeContainer`). No delete escape hatch; the UI shows a disabled Delete entry pointing to the deployment. There is no AI remove-container tool. Consequence, deliberate: containers of Compose projects Shipir does not manage (e.g. started by hand with `docker compose up`) can no longer be removed through Shipir; the UI says to remove them with Compose.

## Review notes (decided)

- **Decided:** all timestamp columns use `TIMESTAMPTZ` (implemented in V1-V4). The drafts used `TIMESTAMP`; `TIMESTAMPTZ` is the usual recommendation in PostgreSQL to avoid time-zone ambiguity, and it maps cleanly to `Instant`/`OffsetDateTime` in Java.
- **Decided:** the `created_by` / `owner_user_id` foreign keys keep no `ON DELETE` rule (RESTRICT), so a user who owns or created hosts, stacks or versions cannot be deleted (history is kept). `stacks.host_id` and `stack_versions.stack_id` stay `ON DELETE CASCADE`.
- **Decided (2026-11-13, shipr-kqbc.77):** a user who sees a host only through deployment grants gets `dockerVersion`, `cpus`, `memoryBytes`, `images` and `volumes` as null from `/hosts/overview` (host facts need a host grant or ADMIN); container counts stay filtered. The environment dashboard hides the Images and Volumes tiles for them instead of showing 0.
- **Decided (2026-11-13, shipr-kqbc.69):** showing env values needs OPERATE on the host or deployment everywhere, not only a non-VIEWER role. `GET .../managed-deployments/{id}/env` returns 403 ENV_VALUES_RESTRICTED for a VIEW-only grant (names stay visible via the detail `envKeys`), container inspect env values (`HostResourcesService.container`) are masked (keys only) without OPERATE on the host or the container's deployment, and `ConfigFileService` env-like files already required OPERATE (unchanged). ADMIN unchanged. The AI redaction lookup (`StoredDeploymentEnvValues`) uses the same `env` check and fails closed for VIEW-only callers.
- **Decided (2026-11-13, shipr-kqbc.63):** if any proxy compose image reference of a host cannot be resolved (variable only in the server environment or in an old version's encrypted env), the guard fails closed: OPERATOR image deletes on that host return 409 `PROXY_IMAGE_UNRESOLVED` and a WARN is logged (host id only, no variable values). ADMIN is unaffected; resolvable references keep the 403 behaviour. Prune is unchanged.
- **Decided (2026-11-13, shipr-kqbc.71):** `POST /api/backup` and `POST /api/account/tokens` need a step-up (`auth/stepup/StepUpService`, reusable, e.g. for kqbc.66). Local-password users send the current password plus a TOTP/recovery code when 2FA is on (`stepUp` object in the body); failures count in `LoginThrottle` scope `STEP_UP` (lockout 429). SSO-linked users re-authenticate at the IdP (`prompt=login`, `max_age`) and the backend accepts the action only if the ID token `auth_time` stored in the session is at most `shipir.security.step-up.sso-max-age` (default 5m) old; otherwise 403 `STEP_UP_SSO_REQUIRED` makes the UI start the IdP flow. Refusals are 403 with codes `STEP_UP_REQUIRED`/`STEP_UP_INVALID`/`STEP_UP_SSO_REQUIRED`/`STEP_UP_SESSION_REQUIRED` (not 401, because the frontend treats any 401 as signed out). API-token callers cannot pass it. Audit rows unchanged, credentials never logged. No migration.
- **Decided (2026-11-13, shipr-kqbc.66):** the `SELF_LINK` refusal is dropped. An ADMIN may link their own account to an SSO identity after step-up re-authentication (`StepUpService`: password plus TOTP if enabled, `stepUp` in the `PUT /api/users/{id}/external-identity` body; failures throttled in scope `STEP_UP`). Audited like other links (`USER_IDENTITY_LINK`). Linking another user is unchanged. Self-unlink stays refused. Session `auth_time` is cleared on local/2FA login and on self-link.
- **Decided (2026-11-13, shipr-kqbc.62):** SSO-linked users are SSO-only: no local password change/reset (UI hidden with explanation, backend already refuses) and MFA is the IdP's responsibility (local TOTP is not applied to OIDC logins; the Account page hides the local 2FA card too). The group-to-role mapping at SSO login never demotes, denies or disables the last enabled ADMIN: `OidcUserResolver` keeps ADMIN (also when no group matches), logs a WARN without secrets and writes an `OIDC_ROLE_KEPT_LAST_ADMIN` audit row; the login succeeds (previously `LAST_ADMIN` error redirect). A non-last ADMIN is demoted as before. The link dialog warns that the role then follows the IdP groups. Documented in the README.
- **Decided (2026-11-13, shipr-kqbc.57):** Pull & redeploy is two steps for an ADMIN so their approval covers exactly the files they saw. `POST .../git/pull` (OPERATE) fetches into the checkout without deploying and returns `{commitSha, graphHash}`; the dialog shows the post-pull files. `POST .../git/redeploy` with `{commitSha, graphHash}` does not fetch again and deploys only if the checkout still hashes to `graphHash`, else 409 `FILES_CHANGED_SINCE_REVIEW` (the UI explains and pulls again). An ADMIN without that body gets 409 `REVIEW_REQUIRED` (this includes the AI tool `git_redeploy_deployment` run by an ADMIN, which has no review step; OPERATORs keep the one-step flow because they never approve files). Step 2 never fetches: the checkout's HEAD must equal the reviewed `commitSha` (local read) and the graph must hash to `graphHash` both before and after the files are written, else 409 `FILES_CHANGED_SINCE_REVIEW`. A null `graphHash` (unhashable graph, kqbc.53: no approval is stored) is accepted only while the graph is still unhashable and HEAD matches, so those ADMIN redeploys keep working. The AI tool answers an ADMIN with a message pointing to the UI. The checkout stays on the pulled commit after step 1 if the dialog is cancelled; the next run realigns it.
